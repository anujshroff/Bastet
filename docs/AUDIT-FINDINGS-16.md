# Critical

## P1 — O1's overlap guard excludes the row's own Azure resource id, so an in-place `subnet update --address-prefixes` still lands the row in the deletable list; reconcile archives it while ARM holds the range, and BASTET then hands the range out `[x2]`

**Citation:** [`src/Bastet/Services/Azure/AzureReconciler.cs:757`](../src/Bastet/Services/Azure/AzureReconciler.cs#L757) — the `!string.Equals(c.Owner.ResourceId, snapshot.AzureResourceId, ...)` conjunct in `FindLiveOwnerOfRange`'s overlap fallback. **Confidence: confirmed.** Found by five beats independently (`logic-data-integrity`, `azure-integration`, `regression-correctness`, `regression-tests`, `dead-code-residue`).

**Scenario.** Azure subnet `rig-p16deepreg-a` holds 10.219.1.0/24 and is imported. An operator narrows it in place — `az network vnet subnet update --address-prefixes 10.219.1.0/25`, the ordinary way to re-carve, which preserves the ARM resource id. `EvaluateSubnetLevel` returns `SubnetPrefixChanged`. `FindLiveOwnerOfRange`'s exact index misses (no live subnet carries the string `10.219.1.0/24`), and the overlap fallback then walks `livePrefixesByVNet` **skipping every candidate whose `Owner.ResourceId` equals the row's own** — which is exactly the subnet still holding 10.219.1.0/25. It returns null, so the row goes to `plan.Items` rather than `plan.ReviewItems`, is offered for deletion, produces no `rangeStillAllocated` warning, and `IsAbsenceStatus(SubnetPrefixChanged)` is false so `ConfirmProposedDeletionsAsync` never re-reads ARM about it either. Both defences O1 named are silent. The remarks that justify the exclusion (`:699-702`, *"A row whose own recorded resource still owns the range is not stale in the first place and never reaches here"*) are true for the equality arm and false for the overlap arm: `EvaluateSubnetLevel` tests membership of the *exact* recorded prefix, so a row can be stale while its own resource still holds a subset or superset. Widening reproduces identically and is sharper — a single scan then contains both "you may archive this row" and "Azure owns this range, which no BASTET subnet records."

**Reproduction.** Own port 5941, own catalog `bastet_v16o1`, unmodified HEAD `1a31228`, SP1 credentials, live ARM and real SQL Server. Fixture `rig-v16o1-vnet` 10.231.0.0/16 with subnet `rig-v16o1-sub` 10.231.1.0/24.

1. `POST /Subnet/BulkCreateFromAzurePlan` → `{"success":true,"createdTargets":1,"createdChildSubnets":1}`; baseline `POST /Azure/ReconcileScan` → `items:[] reviewItems:[] warnings:[]`, clean.
2. `az network vnet subnet update ... --address-prefixes 10.231.1.0/25` → ARM returns the **same** id, prefix now /25.
3. `POST /Azure/ReconcileScan` → `canCommit: true`, `items:[{subnetId:2, cidr:24, statusName:"SubnetPrefixChanged", reason:"The Azure subnet still exists but its address prefix is now 10.231.1.0/25, not 10.231.1.0/24.", suggestedAzureResourceId:""}]`, `reviewItems:[]`, `warnings:[]`.
4. `POST /Subnet/BulkDeleteStaleAzureSubnets` with the plan's own verdict → `200 {"success":true,"targetsDeleted":1,"subnetsArchived":1}`. SQL: row gone from `Subnets`, present in `DeletedSubnets`, which has no `AzureResourceId` column and no restore path.
5. `GET /Subnet/Details/1` → Unallocated IP Ranges renders a single row `10.231.0.0 – 10.231.255.255, 65,534 IP addresses, [Create Subnet]`.
6. `POST /Subnet/Create {10.231.1.0/26, ParentSubnetId:1}` → 302, row persisted, while `az network vnet subnet show` concurrently returns `10.231.1.0/25`.
7. **A/B control, same VNet, same geometry, one variable.** The same /24-recorded-vs-/25-live overlap reached by delete-and-recreate (new resource id) returns `canCommit: false`, `items: []`, and a `RangeStillAllocatedInAzure` review row plus the withheld warning. The guard fires for the changed-id case and not for the same-id case; the only difference is the conjunct at :757.

**Fix.** Stop excluding the row's own resource id from the **overlap** walk; exclude only the degenerate case the remarks actually describe (same resource, *identical* recorded prefix — which the exact index above has already handled):

```csharp
AzureLivePrefix? overlapping = candidates.FirstOrDefault(c =>
    !(string.Equals(c.Owner.ResourceId, snapshot.AzureResourceId, StringComparison.OrdinalIgnoreCase)
      && string.Equals(c.Prefix, recorded, StringComparison.OrdinalIgnoreCase))
    && (ipUtilityService.IsSubnetContainedInParent(c.Network, c.Cidr, snapshot.NetworkAddress, snapshot.Cidr)
        || ipUtilityService.IsSubnetContainedInParent(snapshot.NetworkAddress, snapshot.Cidr, c.Network, c.Cidr)));
```

No call-site change is needed for the reason branch: `LiveRangeOwner.Exact` is false here, so `canRelink` stays false and the third reason branch at `:228-233` already reads correctly. Also correct the remarks at `:699-702`, which state a justification holding only for the equality arm. **Cheaper interim** (one line, fail-safe, over-blocks slightly): add `or AzureReconcileStatus.SubnetPrefixChanged` to the `ReviewItems` branch at `:254-256`, making every prefix-drift row review-only. That stops the archive but also stops the legitimate archive of a subnet whose prefix genuinely moved elsewhere — a stop-gap, not the fix.

**Fix soundness — sound, verified independently.** Built in a scratch copy: 0 warnings, `dotnet test` **892 passed / 0 failed** (identical to baseline), and the patched build converted the reproduced failure into `canCommit: false`, `items: []`, a correctly-worded `RangeStillAllocatedInAzure` review row, and correctly **no** Re-link suggestion. Over-blocking was checked specifically and none was found: the only rows newly withheld are those whose own live Azure subnet overlaps the recorded range, and archiving any of those would by construction leave allocated space reported free; a prefix that moved to a genuinely non-overlapping range still produces a deletable item, and dropping one prefix from a multi-prefix subnet leaves that row deletable. Two notes for the implementer. (1) The proposed exclusion clause is in practice unreachable and could simply be dropped — for `SubnetPrefixChanged`/`SubnetDeleted` no candidate can carry the row's own id *and* the recorded prefix, and for VNet-level statuses the row's id is a VNet id while every candidate owner is a subnet id. Keeping it is harmless and self-documenting, not load-bearing. (2) The claim "no change is needed at the call site" is right about the per-item reason and wrong about the aggregate warning at `:274-278`, which asserts the withheld ranges are *"still assigned in Azure under a different resource"* — false for this case once the fix lands. Reword it to cover both; see **P8**, which is that sentence's own finding.

**Owner decision.** Nothing repairs rows this path has already archived: `DeletedSubnets` has no restore and the archive drops `AzureResourceId`. This needs a decision from you and here is what it costs — the code fix is four lines and measured green, but recovering an already-archived row means either a one-off admin repair action or hand-written SQL, the same open item O1/O2/O3 left on round 15's watch list.

## P2 — `AccountsFor`'s containment arm silences the inbound check for any Azure range inside an ordinary BASTET row, including a row whose own free-space table prints that range as entirely unallocated `[x1]`

**Citation:** [`src/Bastet/Services/Azure/AzureReconciler.cs:623`](../src/Bastet/Services/Azure/AzureReconciler.cs#L623) — the containment arm's `IsSubnetContainedInParent` test. **Confidence: confirmed.**

**Scenario.** `ReportAzureRangesNoBastetSubnetRecords` exists because BASTET's free-space table is offline-safe and cannot know what Azure holds; the Details banner says so and tells the operator to run reconcile before allocating. The containment arm treats **any** non-VNet-linked BASTET row containing the range as recording it, with no test of whether BASTET actually presents that range as allocated. A hand-created aggregate with no children and `IsFullyAllocated = false` therefore silences the inbound check for every Azure range inside it. The method's own remarks (`:570-573`) supply the counter-argument: VNet-level targets are excluded from this arm precisely because *"BASTET's own free-space table agrees: it prints the target's range minus its CHILDREN."* That is equally true of an ordinary row. The free-space table does not distinguish a VNet target from an aggregate; `AccountsFor` does.

**Reproduction.** Own port 5931, own catalog `bastet_rch16acc`, HEAD unmodified, SP1. Own Azure fixture `rig-rch16-vnet` 10.70.0.0/16 with subnet `rig-rch16-sub` 10.70.1.0/25. Every write went through the application's own endpoints — no SQL seeding.

1. Imported the VNet prefix only, no subnets ticked, through the real wizard endpoints → `{"success":true,"createdTargets":1,"createdChildSubnets":0}`. Row 1 = 10.70.0.0/16, `IsFullyAllocated=0`, VNet-linked.
2. **Baseline** `POST /Azure/ReconcileScan` → one review item: `AzureRangeNotImported rig-rch16-sub 10.70.1.0/25 | "…owns 10.70.1.0/25, which no BASTET subnet records. BASTET is reporting that range as free space."` Correct.
3. `POST /Subnet/Create {regional-aggregate, 10.70.0.0/18, ParentSubnetId:1}` → 200, no validation error. Row 2: `AzureResourceId` NULL, `IsFullyAllocated=0`, no children. One ordinary form post.
4. **Re-scan, identical request** → `items 0, reviewItems 0, warnings []`. The item is gone.
5. `GET /Subnet/Details/2` → `10.70.0.0  10.70.63.255  16,382 IP addresses  [Create Subnet]`. **Worse than filed:** row 2 has no `AzureResourceId`, so `_UnallocatedRanges.cshtml` renders no Azure caveat banner on this page at all — the operator gets no warning here, not even the deferred one.
6. `POST /Subnet/Create {handed-out, 10.70.1.0/25, ParentSubnetId:2}` → 200, persisted. BASTET handed out a range Azure owns, immediately after the reconciler reported clean.
7. **Secondary limb, also reproduced.** `GET /Azure/BulkGetVNets` annotates that same Azure subnet `Available`, `isSelectable: true`, `reason: null`, while `POST /Azure/BulkImportPreview` on that exact selection returns `canCommit: false` with a plan-wide global error naming the more-specific BASTET parent. So the range is not even importable by the route that would clear it. (That divergence is **P13**'s subject; it compounds here.)

**Fix.** Make the containment arm ask BASTET's own question rather than a weaker one: a containing row accounts for an Azure range only when BASTET does **not** present that range as free. The finding proposed accepting the containing row only when `existing.IsFullyAllocated` is true; see the correction below before implementing that. Ranges covered by a genuine child are already handled by the equality arm and by a deeper containing row that is itself the record. The item is clearable by the correct action: creating or importing a BASTET subnet for the range makes the equality arm match, and a plain `/Subnet/Create` produces a row with a NULL `AzureResourceId` that satisfies it. **Not a cheaper interim, and it should not be taken:** changing the Details page to withhold the Create Subnet button on unreconciled ranges leaves the reconciler still answering wrongly and only edits the page that displays the consequence.

**Fix soundness — the offered predicate is unsound; take the corrected one.** `existing.IsFullyAllocated` is a proxy for "BASTET shows no free space here", and the two come apart in a state the verifier reproduced. With a row 10.60.0.0/18 (not fully allocated) holding children 10.60.1.0/25 and 10.60.1.128/25, the free-space table correctly does **not** offer 10.60.1.0/24 and today's reconciler is correctly silent — but under the proposed gate nothing accounts for the /24 (parent not fully allocated, neither /25 contains it, the target is VNet-level), so it becomes a review item that is false on the finding's own criterion. The clearability argument fails there too: `POST /Subnet/Create {10.60.1.0/24, ParentSubnetId:2}` is **refused** (verified: no row written) because the two /25s occupy it, and the only remaining escape — marking the /18 fully allocated — would hide roughly 16k addresses of genuine free space elsewhere. That trades today's false silence for permanent unclearable noise, which is the "an operator who cannot silence a warning stops reading warnings" failure the remarks were written to avoid. **The correct predicate is the one the item's own text asserts:** does BASTET's unallocated-range computation — the same one that renders `_UnallocatedRanges.cshtml` — offer any part of this Azure range under any row? Compute the free space of the deepest row containing the range (or of the whole tree once) and report only when the Azure range intersects it. That is exact rather than approximate: it stays silent on the tiled case, reports the childless-aggregate case reproduced above, and every item it raises is clearable by creating or importing a subnet for the offered range, because "offered as free" is precisely the condition under which that creation succeeds. `IsFullyAllocated` may be a fast pre-filter on top of that, never the test. Blast radius in the dangerous direction is nil either way: `AccountsFor` has one caller, it only ever adds report-only review items with `SubnetId = 0`, and those ids already flow into the withheld set, so tightening it cannot cause a deletion or refuse any operation that works today.

**Owner decision.** Whether to accept a per-unrecorded-range review item under coarse aggregates (safety) or keep today's silence (quiet scans). The reproduced consequence of today's setting is that BASTET allocated 10.70.1.0/25 while Azure held it and the scan reported nothing. The containment arm is documented at `:569-575` as a deliberate anti-noise choice, so trading that noise away is a product call — but the current setting is reproducibly wrong output on the exact question the product exists to answer.

## P3 — The bulk import wizard states *"All subnets in this prefix are already imported"* over Azure subnets that were never imported, hiding the only text that says why they cannot be `[x1]`

**Citation:** [`src/Bastet/Views/Azure/BulkImport/_BulkScripts.cshtml:280`](../src/Bastet/Views/Azure/BulkImport/_BulkScripts.cshtml#L280). **Confidence: confirmed.**

**Scenario.** With the *"Hide unavailable"* switch on, `shownSubnets` is `containedSubnets.filter(s => s.isSelectable)`. When that empties the list, line 280 prints the sentence as an unqualified statement of fact. But `isSelectable === false` covers two entirely different verdicts from `AnnotateSubnet`: `AlreadyImported` (the row really was imported from this Azure resource) and `Blocked` (*"Would contain existing Bastet subnet …"* / *"Bastet subnet 'X' already uses …"*, neither of which has ever been imported). A prefix whose every Azure subnet is `Blocked` therefore renders the false sentence, and the red **Cannot import** badge plus its reason — the only text saying what is actually wrong — is filtered out of the DOM. The trigger is not exotic: the `Blocked` branch fires whenever an Azure subnet's prefix matches a BASTET row carrying a different or absent `AzureResourceId`, and since Azure has no subnet-rename operation, renaming is delete-and-recreate under a new ARM id, which lands on that branch for every previously imported subnet in the VNet.

**Reproduction.** Own port 5863, own catalog `bastet_verif16z`, precondition built through supported UI only — no SQL writes. Azure VNet `rig-p16uijs-a` 10.171.0.0/16 with `rig-p16uijs-s1` 10.171.1.0/24 and `rig-p16uijs-s3` 10.171.3.0/24. Bulk-imported the prefix alone, then created `handmade-row` 10.171.1.0/24 and `partial-overlap-row` 10.171.3.128/25 through the ordinary `/Subnet/Create` form. Playwright/Chromium, same page, no reload:

Switch **off** (correct):
```
rig-p16uijs-a 10.171.0.0/16  Will update existing
rig-p16uijs-s1 10.171.1.0/24  Cannot import
Bastet subnet 'handmade-row' already uses 10.171.1.0/24.
rig-p16uijs-s3 10.171.3.0/24  Cannot import
Would contain existing Bastet subnet 'partial-overlap-row' (10.171.3.128/25), which would create an invalid hierarchy.
```
Switch **on**:
```
rig-p16uijs-a 10.171.0.0/16  Will update existing
All subnets in this prefix are already imported.
```
The prefix checkbox is `disabled: False` in both states, so the branch is not on a dead path. Ticking it and committing gives step 3 rendering *"No child subnets selected."* with no mention that two Azure subnets were refused, then the green banner *"Bulk import succeeded: created 0 VNet target subnet(s), created 0 Azure child subnet(s)…"* over a commit that wrote nothing (`SELECT COUNT(*) FROM Subnets` = 3 before and after, all `LastModifiedAt` still NULL), while `/Subnet/Details/1` still lists 10.171.2.0 – 10.171.3.127 (384 addresses) as unallocated with a Create Subnet button over half of Azure's /24. ## P15 — The single-VNet wizard creates two BASTET rows with the identical name and identical `AzureResourceId` when a multi-prefix Azure subnet is imported one prefix at a time `[x1]`

**Citation:** [`src/Bastet/Controllers/SubnetController.Azure.cs:261`](../src/Bastet/Controllers/SubnetController.Azure.cs#L261) — `ResolveImportNames`' batch-only `multiPrefixResourceIds` seed; the line that actually lacks the tree check is `:281-282`. **Confidence: confirmed.**

**Scenario.** `ResolveImportNames` decides which posted rows need a range-qualified name purely from the batch being posted. The bulk planner solves the same problem with `multiPrefixResourceIds` **plus** `HasPersistedSiblingFromSameAzureSubnet` (`AzureBulkImportPlanner.cs:54-61`), whose own docstring says it exists *"so this commit's row needs qualifying even though this commit only carries one selection for that Azure subnet."* The single-VNet path never learned that second half — and it is unreachable *not* to hit it, because `AzureController.GetSubnets` filters out prefixes BASTET already records, so a top-up of a multi-prefix Azure subnet always posts exactly one row and the batch-only test can never fire. The natural production trigger is simpler still: an Azure subnet that gains a second prefix after its first import can only ever be topped up one row at a time.

**Reproduction.** Own port 5931, own catalog `bastet_vfy16m`. Fixture: `az network vnet subnet create -n rig-vfy16m-s --address-prefixes 10.88.20.0/24 10.88.21.0/24` (ARM returns `addressPrefix: null`, `addressPrefixes` = both). Both passes driven through the actual wizard with Playwright, nothing hand-crafted.

- Pass 1: wizard offered two rows, both named `rig-vfy16m-s`; ticked the .20 row → *"Successfully renamed parent subnet to 'rig-vfy16m-vnet' and imported 1 child subnets."*
- Pass 2, same UI: the wizard now offered **one** row only (the recorded prefix was filtered out); ticked it → *"Successfully imported 1 child subnets."*
- SQL: `2|rig-vfy16m-s|10.88.20.0|24|…/subnets/rig-vfy16m-s` and `3|rig-vfy16m-s|10.88.21.0|24|…/subnets/rig-vfy16m-s`. Two rows, identical `Name`, identical `AzureResourceId`.
- **A/B against the sibling path:** deleted row 3, posted the byte-equivalent single selection to `/Azure/BulkImportPreview` → the planner named the child `rig-vfy16m-s (10.88.21.0-24)`. Same Azure subnet, same tree state, same operation, two different persisted names.
- **Consequence checked, not assumed.** The rows differ by CIDR everywhere a range is printed (subnet tree, Details child table, plan items). `AzureReconciler.NameList` (`:773-778`) prints bare names and feeds four *"withheld from deletion"* warnings, so that text is the one surface where the two rows are indistinguishable — driven to the actual screen, a warning came back reading `… They have been withheld from deletion: 'rig-vfx1h-vnet', 'rig-vfx1h-m', 'rig-vfx1h-m'.` The reconcile screen's destructive action posts `subnetIds`, not names, so no wrong row can be deleted. Harm is attribution in warning text only; low stands.

**Fix.** Give `ResolveImportNames` the existing tree. It is already `public static` as a test seam, so add an `IReadOnlyList<Subnet>` parameter — the caller has already loaded `treeCache` at `:334` (the whole table, carrying `AzureResourceId`, read before the call site at `:469`) — and OR the planner's predicate into the `sharesAnAzureSubnet` test at `:281-282`: qualify when any persisted row carries the same `AzureResourceId` but a different `{NetworkAddress, Cidr}`. That is the same rule verbatim, which is the point; the durable form is one shared helper called from both sites rather than a second copy. **Cheaper interim:** make `NameList` print `name (network/cidr)` instead of the bare name, removing the only surface where the two rows are indistinguishable without changing any persisted data.

**Fix soundness — sound, verified by applying it.** In a scratch copy the parameter was added, the planner's predicate ORed in verbatim, and `treeCache` passed: `dotnet build` 0 warnings, `dotnet test` **892 passed / 0 failed**, and re-running the identical pass-2 UI interaction persisted `rig-vfy16m-s (10.88.21.0-24)` — byte-identical to what the bulk planner produces. No over-block: the parent target carries a VNet id while children carry subnet ids, so the parent can never trip the predicate; an ordinary single-prefix import has no persisted sibling and is untouched; a `FullyEncompassesVNetPrefix` row is skipped before the predicate is reached. Stated explicitly rather than left as a surprise: the fix qualifies only the newly-added row and leaves the already-persisted first row bare, so the pair reads `rig-vfy16m-s` / `rig-vfy16m-s (10.88.21.0-24)`. That is deliberate, is exactly what the planner already does, and resolves the stated harm since the names now differ. **One correction to the interim:** amending `OwnerList` (`:765-770`) as well is pointless — it lists Azure-side owners (`ResourceId`, `SubnetName`, `VNetName`), which have no network or CIDR and are not the duplicated BASTET rows. Only `NameList` is the affected surface.
