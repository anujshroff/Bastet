## How this audit ran

**Eight beats**, each a lens over the whole codebase rather than a directory: (1) `azure-integration` — discovery, ARM shapes, the reconcile scan against a live subscription; (2) `logic-data-integrity` — the planner's and reconciler's decision rules against the writes they authorise; (3) `regression-correctness` — the round-15 delta (`O1`–`O16`) re-driven against the behaviour it claims; (4) `regression-tests` — whether round 15's new tests pin what their names say; (5) `locking-lifecycle` — `sp_getapplock`, connection lifetime, the guarded save paths; (6) `dead-code-residue` — code shipped but unreachable, and gates relaxed on one side only; (7) `ui-client-js` — the three wizard state machines and what the screen asserts; (8) `security-web` — authorisation, antiforgery, headers, cookies.

**Two independent passes** ran every beat without sight of each other, plus a **deep sweep** on beats 1, 2, 3 and 4 — last round's delta and the surfaces where a regression would be newest and most consequential. That is 8 × 2 + 4 = **20 finders**, all of which returned.

**Tag meaning.** `[x2]` = the same defect was found independently by **both** passes. `[x1]` = found by **one** pass only. **`[x1]` is weak evidence of absence, not evidence of weakness** — a defect on a surface only one pass happened to drive is precisely the defect that reaches production. Thirteen of the fifteen findings here are `[x1]`, including one of the two criticals, the only high, and both mediums. Every `[x1]` candidate therefore got a second verifier on a reachability-and-consequence lens: can a real user reach this without a crafted request, and what do they actually see and lose?

**Adversarial verification with live reproduction.** Verifiers were told to kill findings, not confirm them. Each stood up its own application instance on its own port, its own SQL catalog, and — where the finding touched Azure — its **own** live ARM fixtures rather than replaying the finder's. **All fifteen reproduced on a running instance; none is inferred from reading code alone**, and several were driven through real headless Chromium rather than through hand-built posts (P3, P6, P11, P14, P15 among them). Where a fix could be built it was built and measured: `git archive HEAD` into scratch, patch, `dotnet build --no-incremental`, `dotnet test`, and the scenario re-driven on the patched binary against the same database and the same Azure state. That is how P1's fix was confirmed green (892/892, failure converted to a correctly-worded withheld review item with no Re-link suggestion) and how P5's and P13's offered interims were caught being no-ops or worse.

**Verified discrimination — the counter-test that stops an over-blocking regression passing as a fix.** The RBAC mapping was *discovered*, not assumed: both service principals hold exactly one role assignment each, both at **resource-group** scope, neither at subscription scope, so no inheritance makes the filtering vacuous. ## P1 — O1's overlap guard excludes the row's own Azure resource id, so an in-place `subnet update --address-prefixes` still lands the row in the deletable list; reconcile archives it while ARM holds the range, and BASTET then hands the range out `[x2]` — FIXED

_P1 is fixed and committed. The overlap arm of `FindLiveOwnerOfRange` no longer excludes candidates carrying the row's own Azure resource id. Narrowing or widening a subnet in place — `az network vnet subnet update --address-prefixes`, one CLI call — preserves the ARM resource id, so the subnet still holding the range **is** the row's own resource, and excluding it was excluding the only evidence that mattered. The exclusion is kept for the degenerate same-resource-**and**-identical-prefix case only, which the exact index above has already answered._

_The fix is the one the finding proposed and the verifier confirmed sound, taken verbatim. The verifier's first note — that the retained exclusion clause is in practice unreachable and could simply be dropped — was **not** acted on: it is kept because it documents at the point of use why the exact arm excludes the row's own id and the overlap arm does not, and the two arms sitting three lines apart with opposite treatment is precisely the shape that produced this defect. It is self-documenting, not load-bearing, and the code says so._

_The remarks at `:699-702` were rewritten, which the finding called for and which matters more than the code change. Their old justification — "a row whose own recorded resource still owns the range is not stale in the first place and never reaches here" — is true of the exact range and false of any subset or superset, because `EvaluateSubnetLevel` tests membership of the **exact** recorded prefix. That sentence is what made the exclusion look correct in review. It now states the distinction explicitly and names the in-place-update case._

_**Sibling sweep** (`grep -rn` for `Equals(o.ResourceId`, `Equals(c.Owner.ResourceId`, `snapshot.AzureResourceId` across `src/`, plus every caller of `FindLiveOwnerOfRange` and every bidirectional `IsSubnetContainedInParent` pair). Two self-exclusions exist in the codebase and both are in this one method: the exact arm at `:750`, which is correct and untouched, and the overlap arm at `:769`, which is the defect. `FindLiveOwnerOfRange` has exactly one caller. **The sweep's real result is the VNet-level sibling:** `EvaluateVNetLevel` asks the same question through `OverlapsRecorded` (`:667`, called at `:825`), resolving the VNet by the row's **own** `AzureResourceId` and deliberately **not** excluding it — which is exactly the behaviour this fix restores at the subnet level. The two levels were answering the same question differently; they now agree. Nothing else in `src/` implements this rule._

_**Strings checked** (step 6). The per-item reason is unaffected: the overlap branch at `:228-233` is already direction-neutral and cause-free, and reads correctly when the owner is the row's own subnet — driven output "Azure subnet 'sn-a' … now holds 10.231.1.0/25, which overlaps the recorded range 10.231.1.0/24". **One string is made false in a new way by this fix and is not repaired here:** the aggregate warning at `:275` asserts the withheld ranges are "still assigned in Azure under a different resource - which is what a subnet rename looks like". After this fix that sentence also covers same-resource re-carves, where both clauses are false. That sentence is **P8**'s entire subject, it is filed with a corrected replacement wording, and it is fixed there rather than pre-empted here — this entry records the dependency so the intermediate state is deliberate and traceable rather than discovered. The reason text's trailing remedy ("correct this subnet to match Azure") is likewise false, and is **P9**'s subject._

_Not done, deliberately, and it is the owner's call rather than the round's: **nothing recovers rows already archived by this path.** `DeletedSubnets` has no restore and the archive does not carry `AzureResourceId`, so a row this defect archived cannot be repaired through any screen. Closing that means either a one-off admin repair action or hand-written SQL at release time. It is the same open item O1/O2/O3 left on round 15's watch list, now for the third round, and it is why P1 is graded critical rather than high: the wrong output is not merely wrong, it is terminal._

_Tests: 892 → 894. Both fail against the unfixed reconciler with the row in `plan.Items` and `ReviewItems` empty — the archive being offered, which is the defect. `SubnetPrefixChanged_WhereTheRowsOwnAzureSubnetStillHoldsPartOfTheRange_IsWithheld` covers the narrowing direction and additionally asserts the review reason names the live `/25` and that **no** Re-link suggestion is offered, since an overlapping owner holds a different range. `SubnetPrefixChanged_WhereTheRowsOwnAzureSubnetNowHoldsAWiderRange_IsWithheld` covers widening. ## P2 — `AccountsFor`'s containment arm silences the inbound check for any Azure range inside an ordinary BASTET row, including a row whose own free-space table prints that range as entirely unallocated `[x1]` — FIXED

_P2 is fixed and committed. `AccountsFor` is gone, replaced by `IsRangeRecordedByBastet`, which asks the question the item's own text asserts: does BASTET's free-space computation offer any part of this Azure range? It is answered with `CalculateUnallocatedRanges` — **the same call that renders the Details page** — so the reconciler and the screen cannot disagree about what is free. That function now has exactly two callers, `SubnetController.Read` and the reconciler._

_**The predicate the finding offered was not taken, because the verifier proved it wrong.** Gating on `existing.IsFullyAllocated` breaks on a partially tiled parent: a /18 holding 10.60.1.0/25 and 10.60.1.128/25 is not fully allocated, yet its free-space table correctly does not offer 10.60.1.0/24. Under that gate the /24 becomes an item that is false on its own wording and cannot be cleared — creating 10.60.1.0/24 is refused because the two /25s occupy it, and the only escape is marking the /18 fully allocated, which hides real free space elsewhere. `ARangeFullyCoveredByRowsInsideIt_IsNotReported` pins that case, and it is the test that decides the shape of the fix._

_`IsFullyAllocated` survives in one place only, as a **silencer**: a row marked fully allocated cannot receive children at all (`SubnetController.Helpers.cs:197` refuses it outright), so BASTET cannot hand the range out. That direction is sound; the positive test is what it cannot support. `ARangeUnderAFullyAllocatedRow_IsNotReported` pins it._

_**The owner decided to report.** The question put was: Azure has a subnet BASTET has no row for, BASTET has a bigger block covering that area — say it, or stay quiet? Reporting means one line per Azure range BASTET has no record of on the first scan after this change, each clearing for good once it is imported or a subnet is created for it. Staying quiet means the reproduced defect stands: BASTET created 10.70.1.0/25 while Azure held it, immediately after the scan reported clean. The decision was **report**._

_**Three existing tests asserted the opposite answer and were inverted, which is the substance of this change rather than an afterthought.** `ARangeContainedByACoarserBastetSubnet_IsNotReported` argued "an IPAM routinely records a coarser allocation than Azure carves out of it" — but a /18 with nothing under it does not record 10.90.77.0/24; open its Details page and that range is printed as free with a Create Subnet button, and creating there succeeds while Azure holds the addresses. It is now `ARangeInsideACoarserRowThatNothingRecords_IsReported`. `AHandReserveInsideTheVNetPrefix_StillAccountsForTheRange` (shipped by N3 as a false positive to suppress) is now `AHandReserveInsideTheVNetPrefixWithNothingUnderIt_IsReported`. `WhenNoVNetPrefixContainsTheRange_AContainingRowStillAccountsForIt` is now `ARangeOutsideEveryVNetPrefixThatNothingRecords_IsReported` — its stated reason was that such items are unclearable, and under the free-space test they are clearable: create 172.16.5.0/24 under the /16 and the item goes away._

_**Sibling sweep** — and it answers a question round 15 left open on the watch list, which asked whether any other consumer of "BASTET records this range" uses a proxy rather than the free-space computation. Grepped `CalculateUnallocatedRanges` and every non-test `IsFullyAllocated` read across `src/`. **No other consumer uses a proxy.** The four planner reads (`AzureBulkImportPlanner.cs:309, 333, 531, 580`), `SubnetController.Read.cs:138`, `HostIpValidationService.cs:226` and `SubnetViewModels.cs:113-114` all ask "can this row receive children or host IPs", which is what the flag actually means and is the same sound direction used here. `AzureReconciler` was the only place the flag or a bare containment test stood in for "not offered as free", and it no longer does._

_**Strings checked** (step 6). The item's own text — "…owns 10.70.1.0/25, which no BASTET subnet records. BASTET is reporting that range as free space." — was previously the wrong thing to say in the tiled case and is now true by construction, because the free-space computation is what decides whether it is emitted. The trailing remedy sentence appended to it is untouched here and is **P10**'s subject: it omits the host-IP arm, so it still tells the operator to import a target the wizard refuses._

_**Two behaviour changes recorded rather than buried.** (1) An Azure range outside the VNet's declared address space, reachable when a credential sees only part of a subscription, now produces an item where it was silent. It is clearable, and the old fallback's justification does not survive the new predicate. (2) `VNetPrefixContaining` became dead with the `vnetPrefix` parameter and was deleted — the "is the containing row inside the VNet prefix" question no longer decides anything, because the deepest containing row is used instead of any containing row, which was the real fix for the ancestor case._

_Host IP assignments are deliberately not fed to `CalculateUnallocatedRanges` here: the snapshot carries `HasHostIpAssignments` as a bool, not the addresses. Omitting them makes the computed free space **larger**, so the reconciler reports where it might otherwise stay silent. That is the safe direction for this check and is why the approximation is acceptable._

_Tests: 894 → 897. Three inverted as above, three added: the tiled counter-test, a half-covered case that must still report (one /25 inside the Azure /24 leaves the other half free), and the fully-allocated silencer._

_**All four verifier corrections taken.** (1) The predicate is not `-2`. It is timeout **or** transport failure - `-2, -1, 20, 64, 121, 233, 10053, 10054, 10060` - because a connection reset after the server committed is exactly as ambiguous. The watch list said this predicate "has not been written down anywhere"; it is written down now, once. (2) The stale-token trap is closed. (3) Create paths get wording only, and the code says why: no key to re-read by. (4) `SQL_TIMEOUT_ERROR_NUMBER` was a `private const` in the locking service so "reuse it" would not compile; it is now `SqlSaveOutcome.CommandTimeout`, consumed by that service, so the copies cannot drift._

_**The stale-token fix is placed better than proposed.** The verifier wanted the re-read and `ModelState.Remove` added to the generic catch. But the block that runs last on every failure path already re-reads with `AsNoTracking` and assigns `viewModel.RowVersion`; its own comment calls it "what actually reaches the view". Only the POSTED token needed clearing from `ModelState`, which the tag helper prefers. One line there covers every failure path, including ones no catch covers._

_**Sibling sweep, and the three siblings were FIXED rather than deferred.** Sweeping every `catch (Exception` on a guarded write turned up three more that assert something stronger than the four filed: `BulkAzure.cs` and `AzureReconcile.cs` both ended "**and no changes were saved**", and `Azure.cs` reported an unexpected error the same way. _**Driven against real SQL Server, both halves, no fault injection.** A sqlcmd session held `BEGIN TRAN; SELECT ... WITH (UPDLOCK, HOLDLOCK); WAITFOR DELAY`, so guarded reads ran and only the UPDATE queued past the 30s command timeout. (1) The branch fires on the real shape: `POST /Subnet/Edit/1` Cidr 8 → 9 returned HTTP 200 in **30.1s** carrying "could not confirm", where HEAD said "Error updating subnet." ## P15 — The single-VNet wizard creates two BASTET rows with the identical name and identical `AzureResourceId` when a multi-prefix Azure subnet is imported one prefix at a time `[x1]`
