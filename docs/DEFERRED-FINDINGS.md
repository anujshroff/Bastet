Cause: at AzureBulkImportPlanner.cs:548-550 the round-20 waiver lets a row with host IPs through when the exact row is linked to this VNet and every selected subnet is "already linked"; LinkedRowForSameAzureSubnet (:426) counts the target row itself as that link when the posted subnet id equals the VNet id; :635 then sets WillMarkFullyAllocated, and BulkAzure.cs:372 writes the flag without ValidateSubnetCanBeFullyAllocated. The wizard client only ever posts the ARM subnet id from the inventory (_BulkScripts.cshtml:443-451), ARM subnet ids always end in /subnets/<name>, and the unique (NetworkAddress, Cidr) index means no other row can match, so only an Admin posting JSON by hand with an ARM-impossible id reaches the write; no real operator gets there through the wizard. This breaks §5 twice: "Reconcile and the bulk import wizard are clients of the IPAM, not privileged writers. Every change they make goes through the same validation a manual operation goes through. Any Azure-driven write that reaches the database without the base validation is a defect, whatever it was trying to achieve.", and "Every write path for a field must accept and refuse exactly the same input. Create, Edit, the bulk import commit and any API caller are siblings." It disproves the premise 23-refuted-a was killed on (that WillMarkFullyAllocated is set only after the planner refuses host IPs). The result is a contradictory state the operator sees on one screen and can clear with one click; no address space is lost or double-allocated.
