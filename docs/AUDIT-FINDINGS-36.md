## M1 — After OIDC sign-in, Bastet redirects the browser to an off-site scheme-relative URL taken from the request path `[x1]`
**Where:** src/Bastet/Program.cs:173, src/Bastet/Program.cs:198, src/Bastet/Controllers/AccountController.cs:24
**Wrong by:** §5: "When one decision has two implementations they drift, and the drift is invisible until the two are compared." Where an auth transition may send the browser is decided by Logout's local-URL rule on sign-out and by nothing on sign-in.
**Breaks:** An unauthenticated visitor opens a Bastet URL whose path begins with two slashes, for example https://bastet.example//evil.example/phish. That path matches no endpoint, so the fallback policy (Program.cs:198, SetFallbackPolicy(RequireAuthenticatedUser)) challenges it and the OIDC challenge records the raw request path as the post-sign-in return target. After the user signs in at the real IdP, /signin-oidc answers 302 with Location //evil.example/phish, which the browser resolves as a scheme-relative URL on another host. The only Bastet code the return target passes through before that redirect is OnTicketReceived (Program.cs:173), which checks nothing — it only trims saved tokens to the id_token. Logout already validates its returnUrl with Url.IsLocalUrl + HttpHeaderValue.IsValid (AccountController.cs:24-28), so "an auth transition only sends the browser to Bastet's own pages" is implemented for sign-out and missing for sign-in: one decision, two implementations, and the sign-in half is absent. A victim who clicks a crafted link to the real Bastet host is delivered to an attacker origin after authenticating. The auth cookie is httpOnly/SameSite=Lax/origin-scoped and is not sent cross-origin, so there is no direct token theft, but it is a genuine post-auth open redirect / phishing enabler.
**Repro:** Truth ran the unmodified 0aa175d build in Production on http://127.0.0.1:21331 (cookie+OIDC) against a local mock OIDC IdP over HTTPS, with all non-loopback egress blocked, driving it two ways: raw sockets forging the secure correlation/nonce cookies while preserving the double-slash path, and real Chromium via Playwright. Both /Subnet and //evil.example/phish returned 302 to the IdP authorize endpoint (positive control: the fallback challenge works). After completing sign-in, /signin-oidc answered: candidate //evil.example/phish → 302 Location: //evil.example/phish with the .AspNetCore.Cookies auth cookie set; control /Subnet → 302 Location: /Subnet (local); control /%2F%2Fevil.example/phish → 302 Location: /%2F%2Fevil.example/phish (local). In Chromium the top frame issued a navigation request to http://evil.example/phish (is_navigation_request=True; requestfailed net::ERR_NAME_NOT_RESOLVED — off-origin, failing only because the host is unresolvable on the air-gapped rig), while the benign control landed on http://127.0.0.1:21331/Subnet. Reach reran over HTTPS on https://127.0.0.1:21340: malicious //evil.example/phish → 302 Location //evil.example/phish; positive control /Subnet/Details/5 → 302 Location /Subnet/Details/5; negative control /%2F%2Fevil.example/phish → stayed local. Over plain HTTP the same flow instead failed with "Correlation failed" → /Account/SignInFailed, because the OIDC correlation/nonce cookies are Secure;SameSite=None and cannot round-trip over HTTP, so the redirect manifests on the realistic HTTPS OIDC deployment. The finder adds that a path given as /\evil.example/phish is normalised by Chromium to // and gives the same result, and that Logout controls returnUrl=//evil.example, /%09/evil.example, %2F%5Cevil.example, https://evil.example/ and /%E2%80%A8/evil.example all ended at /Account/SignedOut while returnUrl=/Subnet returned to /Subnet — Logout's local-URL rule works and only the sign-in transition lacks it.
**Fix:** In the existing OnTicketReceived handler (Program.cs:173), replace context.ReturnUri with "/" unless it passes the same local-URL rule Logout applies to returnUrl (Url.IsLocalUrl semantics: starts with a single '/' not followed by '/' or '\', no control characters, plus HttpHeaderValue.IsValid). Move that rule into one shared helper called by both Logout and the event, so sign-in and sign-out cannot drift. The base RemoteAuthenticationHandler reads ReturnUri after the event and redirects to it, so this is the correct lever; it introduces no new IPAM mechanism and restores parity with Logout per §5's duplication invariant. No comments, no new configuration; works on plain HTTP and assumes no reverse proxy. Both verifiers judged the fix sound.

**Where:** src/Bastet/Services/FullyAllocatedNote.cs:38, src/Bastet/Services/FullyAllocatedNote.cs:39, src/Bastet/Services/FullyAllocatedNote.cs:25, src/Bastet/Controllers/SubnetController.BulkAzure.cs:374, src/Bastet/Controllers/SubnetController.Azure.cs:27, src/Bastet/Controllers/SubnetController.Azure.cs:11, src/Bastet/Models/ViewModels/EditSubnetViewModel.cs:29, src/Bastet/Controllers/SubnetController.Edit.cs:64, src/Bastet/Views/Subnet/Edit/_EditForm.cshtml:55, src/Bastet/Models/ViewModels/SubnetViewModels.cs:26, src/Bastet/Controllers/HostIpController.cs:706, src/Bastet/Controllers/SubnetController.Azure.cs:28, src/Bastet/Controllers/SubnetController.Edit.cs:242
**Wrong by:** §5: "Every write path for a field must accept and refuse exactly the same input. Create, Edit, the bulk import commit and any API caller are siblings: a rule on one and not the others produces a tree the app itself populated but its own form will not re-enter."
**Breaks:** When the bulk import marks a target fully allocated, FullyAllocatedNote.Append joins the existing description + "\n" + note (FullyAllocatedNote.cs:38-39) and accepts the result at 1000 characters or fewer, counting the LF as one character. Descriptions typed into the Create or Edit forms are stored with CRLF line breaks, because browsers post textarea line breaks as CRLF, and [StringLength(1000)] (EditSubnetViewModel.cs:29) counts that CRLF as two. From then on every Edit of that subnet re-posts the description as 1001 characters and the server refuses with "Description cannot be longer than 1000 characters", even when the operator only renames the subnet or changes its tags. The client-side check counts 1000 and lets the submit through, and nothing is saved. This is a record the app populated through one write path that its own form will not re-save (§5 write-path parity). Nothing is lost; the operator recovers by deleting one character from text the import wrote.
**Repro:** Truth drove the real 0aa175d UI on port 21560: created enc-hand 10.15.0.0/24 with a typed description, ran the /Azure/BulkImport wizard (prefix "Will update existing / Will import into existing Bastet subnet 'enc-hand'."; snet-all "Covers the whole VNet prefix, so it marks the target fully allocated instead of being created."; Preview ExactMatch, willMarkFullyAllocated=true; Commit 200 "...marked 1 target(s) as fully allocated."), and SQL then showed the row at length 1000 with 1 CR and 2 LF. Three controls pin the cause: a form-written row of identical stored length (1000) saved (ctl-hand → /Subnet/Details/2 "updated successfully"); the byte-identical stored text posted with its bare LF (1000, SHA-256 equal to the DB) returned 302 and saved, so the only extra character is the browser's CR; and an import-written 999 saved. Reach reproduced end to end in Chromium on the unmodified build with real ARM data and pinned the boundary exact (912 saves, 913 refuses), and drove a second consequence at any length: the Edit conflict message (SubnetController.Edit.cs:242, Ordinal comparison) told the operator "Description is now ..." after a rename-only import that never touched the description, because the stored and posted texts hash identically once CRLF becomes LF. **Fix:** In FullyAllocatedNote.Append, join with "\r\n" — the line break every form-written description already stores — and keep the combined.Length <= maxLength test, so the stored length equals what the Edit form re-posts and the existing drop-the-note branch runs when it would exceed the cap. IsNote already trims each line, so notes on CRLF lines and legacy LF lines are both recognised. No validation rule changes. The fix does not repair rows already stored at exactly 1000 with a bare LF; they stay until they are shortened. Both verifiers drove the fix on a built copy (at 913 the note is dropped and the flag still set and the rename saves; at 912 the stored value equals the re-post; un-mark/re-import cycles stayed stable) and judged it sound.

## L4 — Key-ring startup lock misses replicas whose connection strings spell the catalog in a different case, so they mint separate keys and reject each other's forms (31-M1 back) `[x1]`
**Where:** src/Bastet/Program.cs:383, src/Bastet/Data/MigrationLockConnectionString.cs:15
**Wrong by:** §5: "When one decision has two implementations they drift, and the drift is invisible until the two are compared." The catalog-to-lock-name rule is lower-cased for the migration lock and verbatim for the key-ring lock.
**Breaks:** Two BASTET instances share one catalog, and their BASTET_CONNECTION_STRING values spell the database name in different case (Database=Bastet on one, Database=bastet on the other). SQL Server catalog names are case-insensitive, so both open the same database and both cold-start against an empty DataProtectionKeys table. Each replica takes its own lock, both read the empty key table, and each mints its own key. When the two first loads land roughly 80-100 ms apart, one replica's re-read misses the other's key and the replicas end up protecting with different default keys. This lasts until restart — exactly the symptom 31-M1 recorded, in a configuration round 17 required the startup locks to handle. §5 duplication invariant: the catalog-to-applock-name rule exists twice and drifted, and §6 lets anyone host Bastet any way they like.
**Repro:** Truth ran the real tree with server collation SQL_Latin1_General_CP1_CI_AS.
