## M1 — After OIDC sign-in, Bastet redirects the browser to an off-site scheme-relative URL taken from the request path `[x1]`
**Where:** src/Bastet/Program.cs:173, src/Bastet/Program.cs:198, src/Bastet/Controllers/AccountController.cs:24
**Breaks:** An unauthenticated visitor opens a Bastet URL whose path begins with two slashes, for example https://bastet.example//evil.example/phish. That path matches no endpoint, so the fallback policy (Program.cs:198, SetFallbackPolicy(RequireAuthenticatedUser)) challenges it and the OIDC challenge records the raw request path as the post-sign-in return target. After the user signs in at the real IdP, /signin-oidc answers 302 with Location //evil.example/phish, which the browser resolves as a scheme-relative URL on another host. The only Bastet code the return target passes through before that redirect is OnTicketReceived (Program.cs:173), which checks nothing — it only trims saved tokens to the id_token. Logout already validates its returnUrl with Url.IsLocalUrl + HttpHeaderValue.IsValid (AccountController.cs:24-28), so "an auth transition only sends the browser to Bastet's own pages" is implemented for sign-out and missing for sign-in: one decision, two implementations, and the sign-in half is absent. A victim who clicks a crafted link to the real Bastet host is delivered to an attacker origin after authenticating. The auth cookie is httpOnly/SameSite=Lax/origin-scoped and is not sent cross-origin, so there is no direct token theft, but it is a genuine post-auth open redirect / phishing enabler.
**Repro:** Truth ran the unmodified 0aa175d build in Production on http://127.0.0.1:21331 (cookie+OIDC) against a local mock OIDC IdP over HTTPS, with all non-loopback egress blocked, driving it two ways: raw sockets forging the secure correlation/nonce cookies while preserving the double-slash path, and real Chromium via Playwright. Both /Subnet and //evil.example/phish returned 302 to the IdP authorize endpoint (positive control: the fallback challenge works). After completing sign-in, /signin-oidc answered: candidate //evil.example/phish → 302 Location: //evil.example/phish with the .AspNetCore.Cookies auth cookie set; control /Subnet → 302 Location: /Subnet (local); control /%2F%2Fevil.example/phish → 302 Location: /%2F%2Fevil.example/phish (local). In Chromium the top frame issued a navigation request to http://evil.example/phish (is_navigation_request=True; requestfailed net::ERR_NAME_NOT_RESOLVED — off-origin, failing only because the host is unresolvable on the air-gapped rig), while the benign control landed on http://127.0.0.1:21331/Subnet. Reach reran over HTTPS on https://127.0.0.1:21340: malicious //evil.example/phish → 302 Location //evil.example/phish; positive control /Subnet/Details/5 → 302 Location /Subnet/Details/5; negative control /%2F%2Fevil.example/phish → stayed local. Over plain HTTP the same flow instead failed with "Correlation failed" → /Account/SignInFailed, because the OIDC correlation/nonce cookies are Secure;SameSite=None and cannot round-trip over HTTP, so the redirect manifests on the realistic HTTPS OIDC deployment. The finder adds that a path given as /\evil.example/phish is normalised by Chromium to // and gives the same result, and that Logout controls returnUrl=//evil.example, /%09/evil.example, %2F%5Cevil.example, https://evil.example/ and /%E2%80%A8/evil.example all ended at /Account/SignedOut while returnUrl=/Subnet returned to /Subnet — Logout's local-URL rule works and only the sign-in transition lacks it.
**Fix:** In the existing OnTicketReceived handler (Program.cs:173), replace context.ReturnUri with "/" unless it passes the same local-URL rule Logout applies to returnUrl (Url.IsLocalUrl semantics: starts with a single '/' not followed by '/' or '\', no control characters, plus HttpHeaderValue.IsValid). Move that rule into one shared helper called by both Logout and the event, so sign-in and sign-out cannot drift. The base RemoteAuthenticationHandler reads ReturnUri after the event and redirects to it, so this is the correct lever; it introduces no new IPAM mechanism and restores parity with Logout per §5's duplication invariant. No comments, no new configuration; works on plain HTTP and assumes no reverse proxy. Both verifiers judged the fix sound.

Separate pre-existing sibling the reach verifier noted, which this fix neither causes nor closes: the forms' maxlength="1000" lets an operator type 1000 characters including a line break, the browser posts 1001, and the server refuses; only normalising line endings to LF at binding would close that, and that change would also need the Edit.cs:242 comparison normalised.

## L4 — Key-ring startup lock misses replicas whose connection strings spell the catalog in a different case, so they mint separate keys and reject each other's forms (31-M1 back) `[x1]`

**Breaks:** Two BASTET instances share one catalog, and their BASTET_CONNECTION_STRING values spell the database name in different case (Database=Bastet on one, Database=bastet on the other). **Repro:** Truth ran the real tree with server collation SQL_Latin1_General_CP1_CI_AS.
