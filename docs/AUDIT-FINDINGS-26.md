## L1 - 25-L1 grant-access panel also fires on the no-credential branch, contradicting the Failed banner on the same screen `[x2]`
**Where:** src/Bastet/Services/Azure/AzureService.cs:48 (root cause); panels at src/Bastet/Views/Azure/BulkImport/_StepSubscription.cshtml:36 and src/Bastet/Views/Azure/Reconcile/_StepSubscription.cshtml:40, unhidden at src/Bastet/Views/Azure/BulkImport/_BulkScripts.cshtml:70 and src/Bastet/Views/Azure/Reconcile/_ReconcileScripts.cshtml:87 on success:true+empty; one root-cause fix at AzureService.cs:48 covers both
**Breaks:** Operator misconfigures the host's Azure credential so DefaultAzureCredential's constructor throws — reproduced with AZURE_TOKEN_CREDENTIALS=bogusvalue, a realistic typo of the documented dev/prod values; AzureArmClientProvider catches and sets Client = null. Opening either wizard page then shows two contradictory messages at once: the server banner (CheckCredential -> Failed) says "Could not authenticate with Azure. Check the credentials and that Azure is reachable from this host." while the client no-subscriptions panel says "This credential cannot see any subscriptions. Grant it access to a subscription and reload this page." The panel fires because AzureService.GetSubscriptions() returns [] for the null client instead of failing, the controller wraps that as success:true with an empty list, and the client treats empty-list-success as NoVisibleSubscriptions. The grant-access remedy is false and unactionable — no credential is signed in, so granting a subscription and reloading changes nothing (rule 3: a message naming a remedy the app refuses). Before 25-L1 the panel read "No subscriptions found. Please check your Azure credentials.", which was true in this branch; the rewording is untrue in a branch the fixer did not have in mind. The deliberately-wrong-secret case is NOT affected (GetSubscriptions throws -> success:false -> truthful error panel), confirmed live.
**Repro:** launch-custom.sh 5062 bastet_beat6_p2 badtokencreds (rig launch env + export AZURE_TOKEN_CREDENTIALS=bogusvalue), then Playwright drive of both pages captured: /Azure/BulkImport visible alerts = "Could not authenticate with Azure. Check the credentials and that Azure is reachable from this host." AND "#bulk-no-subscriptions: This credential cannot see any subscriptions. Grant it access to a subscription and reload this page." (subscription-error panel hidden); /Azure/Reconcile identical with #rec-no-subscriptions. App log confirmed the mechanism: "Failed to create Azure credential; Azure features will be unavailable / System.InvalidOperationException: Invalid value for environment variable AZURE_TOKEN_CREDENTIALS: bogusvalue". Control drive with mode=badsecret (wrong AZURE_CLIENT_SECRET) showed the Failed banner + "Failed to load subscriptions from Azure. Details have been logged." and the grant-access panel stayed hidden on both pages. Verifier independently re-ran both drives (port 5100, catalog bastet_v1_c1) with identical results, including the badsecret control.
**Fix:** In AzureService.GetSubscriptions(), make the _armClient == null branch fail instead of returning [] — e.g. throw new InvalidOperationException("No Azure credential is available. Check the application's Azure authentication configuration.") (the same classification its sibling GetVNetInventory already gives this state at AzureService.cs:81). The controller's existing catch then returns success:false and the client shows the truthful subscription-error panel; no client or view change needed. This also removes a second, drifted implementation of the "is there a credential" classification (CheckCredential says Failed, GetSubscriptions said empty-but-fine), per the product model §5 single-implementation invariant.
**Residue of:** 25-L1
